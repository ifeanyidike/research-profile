I01
An AI assistant combines a model with ordinary application code, data sources and sometimes tools. Training fits the model from examples; inference uses it to produce an output. A fluent output is not proof that a fact or permission was checked. Security depends on what the whole application can read, reveal and change.
Trace one request: authenticate the learner, retrieve only permitted notes, send the allowed context to the model, then display the result safely. The model proposes text; the application enforces identity, ownership and tool permissions. Keep those controls outside the model’s judgement so a mistaken answer cannot grant new authority.

I02
Prompt injection is an attempt to make untrusted text redirect an AI assistant from its authorised task. It may arrive directly in a message or indirectly inside a retrieved document or tool response. A document saying “send all private notes” is still document content, not permission from the learner.
Keep source labels and task boundaries clear, then limit consequences independently: retrieve only allowed data, expose only needed tools and authorise exact actions in application code. A prompt warning can guide the model, but it cannot replace a server-side permission check. The fixed example below requires no model call.

I03
Retrieval-augmented generation (RAG) finds documents and adds them to the context used to answer a question. An embedding represents content numerically so similar items can be ranked. Relevance is separate from permission: B’s private note must not enter A’s context even if it is the closest match.
Authenticate the caller, determine permitted documents, rank within that scope and pass only those texts to generation. Carry document versions and access decisions into caching and deletion rules. Filtering a final answer cannot undo private text already disclosed earlier in the pipeline.

I04
A tool lets an assistant ask application code to perform an operation, such as reading a note or drafting a message. An agent can propose several such steps toward a task. A model-generated proposal is a request to check, not evidence that the learner approved it.
An independent executor checks the signed-in actor, allowed tool, exact arguments, current object access and task limits before acting. Bind any required approval to the actual destination/content and reject changed or expired requests. Retry handling must avoid duplicate effects.

I05
An AI application depends on more than its code: model weights, tokenizer, optional adapters, retrieval data and loading software can all change behaviour. Its supply chain is the path by which those components are obtained, reviewed, built and deployed. A familiar model name does not identify exact bytes or a trusted release.
Record publisher, revision, digest, usage rights and loading settings for each component. Treat added adapters or corpus changes as releases even when the base model stays the same. A matching digest supports byte identity; provenance, executable loading behaviour and semantic trust require separate review.

I06
AI privacy asks which data enters prompts, retrieval, model training, generated outputs and logs, who receives each copy and how long it remains. “Not used for training” and “not stored” are different promises. Embeddings and summaries may still reveal private information.
Start with the task and omit fields it does not need before transmission. Record each recipient and derived copy, restrict access and verify the actual service’s retention/deletion settings. Redaction and encryption help with specific boundaries but do not replace minimisation or ownership checks.

I07
AI security assurance means explaining which security properties are supported by which evidence. A hand-checked executor case can show a particular allow/deny decision; it does not show what a live model will propose or prove resistance to every attack. Resource limits prevent a task from consuming unlimited work.
Define the property, supply fixed cases including legitimate success and check enforcement outside the model. Bound input size, tool calls, elapsed time and retries in application code. Keep mock-policy evidence separate from runtime model evidence and record untested cases.

An AI incident investigation traces the application, model configuration, retrieved sources and tool authority to find what actually happened. A security case links a claim to evidence and its limits. A denied mock proposal demonstrates that case’s enforcement, not a real breach or universal AI safety.
