S01
Threat modelling asks, “What does this system do, what must stay protected and how could that fail?” Identify valuable assets, the people or services involved, entry points and where trust changes. A threat is a possible unwanted event; a vulnerability is a weakness that can enable it; a control reduces its likelihood or impact. Make your assumptions explicit.
Secure design principles help turn a diagram into decisions. Least privilege limits granted authority. Complete mediation checks each relevant access. Fail-safe defaults deny access unless allowed. Defence in depth uses controls with different failure modes. Every control has costs and limits, so connect it to an actual threat rather than collecting controls without a reason.
Draw a private notes service with browser, server, database, and backup store. Mark where identity is established and where note ownership is checked. Consider a stolen session and an accidental public backup. Add one preventive and one recovery control for each, and explain the residual risk after those controls fail or succeed.
A threat model is a revisable argument, not a guarantee. Update it when data flows, dependencies, or assumptions change.
Which is the strongest starting point for a threat model?
The system's assets, behaviour, actors, and trust boundaries
A list of fashionable security tools
A promise that the framework is secure by default
Controls make sense in relation to what the system must protect and where untrusted influence enters.

S02
Encryption uses a key to hide readable data, called plaintext. Symmetric encryption uses shared secret key material to encrypt and decrypt. Hiding the contents does not, by itself, show that the message is authentic or unchanged. Authenticated encryption with associated data (AEAD) protects confidentiality and integrity together. It can also authenticate selected public metadata without encrypting it.
A nonce is a value supplied to an encryption operation whose uniqueness requirements depend on the algorithm. Reusing a nonce with the same key can be catastrophic for common AEAD schemes. Keys need a cryptographically secure random source, appropriate storage, and an established library API. Learn the construction's rules; do not invent your own mode or use predictable random generators for secrets.
With the course's supported cryptography library, encrypt a harmless message and authenticate a record identifier as associated data. Decrypt successfully, then alter the ciphertext or identifier and confirm authentication fails. Record the nonce-generation rule and key lifetime. Treat any authentication failure as failure, not as permission to display partially decrypted content.
Encryption is not a substitute for key management. An exposed key can erase the intended protection.
What should happen when AEAD authentication fails?
Reject the message without using unauthenticated plaintext
Return the plaintext with a warning and continue
Ignore the failure if the ciphertext looks readable
AEAD's authenticity guarantee depends on rejecting failed verification before relying on the data.

S03
A cryptographic hash turns input of varying lengths into a fixed-length digest without using a secret key. Collision resistance concerns how hard it is to find two inputs with the same digest. Preimage resistance concerns finding an input for a given digest. A message authentication code (MAC) instead uses a secret key to authenticate a message. None of these operations is the same job as hiding the message with encryption.
Password storage must resist guessing after a database leak. A unique salt prevents identical passwords from sharing one precomputed result; an appropriate password-hashing function adds configurable computational or memory cost. A salt is not a secret key. Use a maintained password-hashing API and its verification operation rather than designing a fast custom hash loop.
Hash two different harmless messages and compare digests. Then authenticate a message using a standard MAC API and verify that a changed message fails. Finally use the course's password-storage API to store and verify a synthetic password twice with different salts. Explain why unequal stored values can still verify the same password.
A plain hash does not prove who created a message. Anyone able to change the message may also recompute its unkeyed digest.
Why use a unique salt for password hashing?
To prevent reuse of one precomputed guess result across many stored passwords
To make a weak password impossible to guess
To encrypt the password so it can always be recovered
Salts separate stored computations. They do not add password entropy or turn hashing into reversible encryption.

S04
Public-key cryptography separates public information from private secret material. With a digital signature, a private-key holder signs data and others check it using the public key. Key exchange has a different purpose: establishing shared key material. A signature normally leaves the message visible. Encryption alone does not prove who wrote it.
The hard question is often binding a public key to the intended identity. Certificates express such bindings under an issuer's signature and validation rules. A chain is useful only when the verifier trusts an appropriate root and checks relevant names, validity, constraints, and usage. Possessing any mathematically valid key is not enough to impersonate a named service.
Generate a lab signing key with an established library. Sign a short statement and verify it. Change one byte and observe failure. Then compare the successful mathematical verification with a separate identity question: why should a recipient believe this public key belongs to you? Document the trusted channel used to share the fingerprint.
A signature establishes a relationship to a key under assumptions. Its human identity meaning depends on trustworthy key distribution.
What does successful signature verification directly establish?
The message matches a signature produced with the corresponding private key, under the scheme's assumptions
The message is confidential
The signer is necessarily a trustworthy person
Verification binds data to a key. Confidentiality and the real-world identity or trustworthiness of the signer require separate reasoning.

S05
TLS protects communication between endpoints. In a typical authenticated HTTPS connection, the client checks a certificate to help authenticate the server. A handshake establishes keys, and authenticated encryption protects the records sent afterwards. Learn current protocol behaviour from current documentation; use historical lectures for the concepts and versions they actually describe.
Check both the cryptography and its use. A correctly encrypted connection to the wrong host is still wrong. Certificate name checks, trust roots, and validation failures matter. TLS termination at a proxy means the proxy sees plaintext; another segment may need separate protection. Channel security does not prevent an authorised endpoint from mishandling received information.
Draw browser, TLS-terminating proxy, and application server. Mark which segments are encrypted and where plaintext exists. Inspect a legitimate site's certificate using browser tools and identify the subject names, issuer, and validity period. Explain why bypassing a certificate warning removes an important part of the intended authentication argument.
HTTPS does not establish that an application's business logic, dependencies, or content are safe.
A proxy terminates TLS and forwards plain HTTP internally. Where is the original TLS protection boundary?
Between the client and that proxy
Automatically through every downstream service and database
Only around the visible HTML, excluding requests
TLS protects its actual connection endpoints. A downstream connection is a separate channel with separate guarantees.

S06
Authentication checks who or what presents a credential. Authorisation checks whether that person or service may perform a particular action on a resource. A session lets the application recognise an authenticated actor across requests. Least privilege means granting only the authority a task needs, for only as long as it is needed.
Design access checks around actor, action, resource, and context. Deny by default, enforce checks on the server, and consider session expiry and revocation. Multifactor authentication improves the login boundary under its threat model but does not repair a missing ownership check. Service accounts also need identities, limited permissions, and lifecycle management.
Define read, edit, and delete permissions for owners, invited readers, and administrators in a notes service. Turn the matrix into positive and negative tests. Include a signed-in user requesting another user's note and an expired session requesting an owned note. Explain which failure is authentication-related and which is authorisation-related.
Being signed in is not a universal access permission. A valid identity must still be evaluated against each protected operation.
A signed-in learner can edit another learner's private notes. Which control is missing?
Object-level authorisation
Text formatting
A larger password field
The identity may be valid, but the requested action on that particular object lacks permission.

W01
Browser developer tools let you inspect requests, responses, storage and script activity. An intercepting proxy lets you inspect or change HTTP traffic in an authorised lab. Remember where each view sits: the browser may change a request before sending it, while the proxy sees it later at its own point in the connection.
Begin with a baseline request that succeeds normally. Record the actor, target, method, headers, body, response, and visible state change. Change one variable at a time so that you can attribute the result. A local proxy's trusted certificate affects your browser's trust decisions; use a dedicated lab profile and follow the provider's installation and removal guidance.
In a provided training lab, capture a harmless form submission. Repeat it unchanged, then alter one non-sensitive input and compare the response and server-side result. Label each request so the original remains available. Explain which observations are direct evidence and which explanations are hypotheses requiring another check.
An unusual response is not automatically a vulnerability. Establish the violated security property and reproduce it within scope.
Why preserve an unmodified baseline request?
It provides a comparison for attributing the effects of later changes
It guarantees every later response is exploitable
It removes the need to identify the active account
A baseline helps separate normal behaviour from effects caused by a controlled change.

W02
SQL injection happens when untrusted input becomes part of the query’s instructions. If you build SQL by joining input into a command string, the database may interpret part of that input as syntax. Parameterised queries keep the query structure and its values separate. This lets the database treat a supplied value as data rather than a new instruction.
Validation and least-privileged database accounts are useful additional controls, but they do not replace correct query construction. Parameters normally bind values, not arbitrary identifiers such as table names. When an identifier must vary, choose it from a fixed application-controlled mapping. Protect every query path, including background jobs and less-used administrative features.
Use the linked deliberately vulnerable lab, then repair a local query by replacing string concatenation with the database driver's binding API. Test a normal name, a quote-containing name, and the lab's authorised failure case. The corrected version should preserve legitimate punctuation while preventing input from altering query structure.
Deleting quote characters is not a general SQL injection defence and may damage valid data.
What is the primary purpose of SQL value parameters?
Keep input values separate from query syntax
Encrypt the database connection automatically
Grant every query administrator permissions
Binding preserves the code-data boundary. Connection encryption and account permissions are separate controls.

W03
Cross-site scripting (XSS) happens when attacker-controlled content runs as script in another user’s browser context. Reflected XSS returns the input in a response. Stored XSS saves it for later visitors. DOM-based XSS uses an unsafe flow in browser code. Follow the data from its untrusted source to the place that interprets it as code, called the sink.
Use safe text APIs when displaying text. Where markup is required, use a maintained sanitiser under an explicit policy. Output encoding must match its context: HTML text, an attribute, JavaScript, and a URL have different rules. Content Security Policy can reduce some consequences, but it does not justify leaving unsafe insertion paths in place.
In a local preview component, compare assigning a harmless tag-like string through textContent with inserting it as HTML. Draw the source-to-sink path without using real users or public targets. Replace the unsafe sink, then test ordinary text, angle brackets, quotes, and non-ASCII input to ensure the repair preserves intended content.
One generic escaping function is not appropriate for every output context.
A comment is meant to display plain text. Which browser API best preserves that intention?
textContent
An unrestricted innerHTML assignment
Executing the comment with eval
textContent creates text rather than asking the browser to interpret the value as markup or code.

W04
When you are signed in, your browser may automatically attach a session cookie to a request. Cross-site request forgery (CSRF) abuses that behaviour: another site can cause a state-changing request even if it cannot read the response. The server must check that the action was intended and authorised. A request carrying a session cookie is not enough.
Use the framework's CSRF protection, appropriate cookie settings, and suitable origin checks according to the application architecture. State-changing actions should not be implemented as safe navigation GETs. A valid anti-CSRF token must be checked by the server and bound according to the framework's design. XSS can undermine many browser-side CSRF defences, so these topics remain connected.
For the provided lab, list the credentials sent automatically, the action changed, and the missing intent check. In a local repair, enable the framework's CSRF middleware and test a legitimate form, a missing token, and an incorrect token. Confirm the failed requests do not change server state.
Same-origin restrictions on reading responses do not necessarily stop a browser from sending cross-origin requests.
Why can CSRF work even when the attacker cannot read the response?
The harmful effect may occur when the authenticated request is processed
Every request requires the attacker to see the response first
The same-origin policy blocks all cross-origin form submissions
The attacker may need only the side effect. Read restrictions and request-sending rules are different.

W05
The same-origin policy limits what browser scripts can read across origins. CORS lets a server allow selected cross-origin reads; some requests first need a preflight permission check. These rules control browser behaviour, not user identity. They do not replace authentication and do not prevent a non-browser client from sending requests directly.
A CORS policy should reflect the actual trusted origins and credential requirements. Automatically reflecting any Origin header while permitting credentials can expose authenticated data in unsafe configurations. Separately consider whether a request can be sent, whether cookies are attached, whether a preflight is required, and whether script can read the response. Those are related but distinct decisions.
Draw a frontend on one origin and an API on another. Define exactly which origin needs readable responses. Test the allowed origin and a disallowed origin using the course lab. Record network activity separately from script-visible results so that a blocked read is not mistaken for proof that no request reached the server.
CORS does not replace API access checks and is not enforced by arbitrary server-side HTTP clients.
Who primarily enforces CORS restrictions on response access?
The browser
Every command-line HTTP client by universal rule
The database engine
CORS is a browser security mechanism. The server still needs authentication and authorisation for direct callers.

W06
Path traversal happens when a path supplied as input leads outside the directory or resource area the app intended to allow. Parent components, absolute paths, encodings and platform-specific separators can change where it resolves. Check the path’s meaning after the relevant processing. Looking like a child filename is not enough.
Prefer mapping an application-controlled identifier to a stored object rather than accepting arbitrary filesystem paths. If paths are necessary, resolve them according to the platform and enforce containment carefully, including symbolic-link and race considerations. Apply least privilege to the process so that an input-validation defect has a smaller reach.
Inside the provided lab, identify the intended base directory and the point where input becomes a filesystem lookup. For a local repair, replace user-supplied paths with opaque IDs mapped to known files. Test a legitimate ID, an unknown ID, and boundary cases. Verify both the response and which file was actually accessed.
Removing one occurrence of '../' is not a reliable containment strategy. Normalisation and alternate representations can defeat ad hoc filtering.
Which design most directly reduces arbitrary path interpretation?
Mapping an opaque identifier to an application-controlled stored object
Appending input to a base path without checking
Removing only the first parent-directory component
An identifier mapping narrows the operation to known resources instead of treating caller input as path syntax.

W07
A shell interprets command text, including separators, expansions, quotes and redirection. If untrusted input becomes part of that text, it may become an instruction: this is command injection. Passing separate arguments to a program is a different boundary. Understand which component interprets each value instead of assuming all process-launch methods behave alike.
Prefer a library API that performs the operation directly. When starting a process is necessary, use an argument-vector API without a shell and a fixed executable. This removes shell parsing but does not remove every risk: the program may interpret an argument beginning with a dash as an option, and filenames or expressions may have their own syntax. Validate according to the invoked program's contract.
Replace a local shell-based file-counting operation with a language library call. Compare handling of spaces and punctuation in harmless filenames. If the lab requires a process, pass explicit arguments and inspect the tool's end-of-options rules. Explain which interpreter was removed and which input semantics still remain.
Avoiding a shell is a strong improvement, not proof that all possible argument injection has disappeared.
What is the best first alternative to constructing a shell command for a file operation?
Use a language library API for the operation
Add more string concatenation
Run the command with greater privileges
A direct API avoids an unnecessary command language boundary and usually makes validation clearer.

W08
Uploading a file involves more than accepting its name. The app receives bytes and metadata, chooses storage, processes the file and may later serve or execute it. Treat the browser’s filename and content type as untrusted claims. An allowed extension does not prove the format is correct or the file is safe. Even a valid file can trigger a bug in a vulnerable parser.
Use an explicit allowlist of required formats, size limits, controlled storage names, appropriate content verification, and safe handling paths. Store uploads where they cannot become executable application code. Serve downloads with suitable headers and authorise access to the stored object. Consider scanning and isolated processing as additional controls with known limits.
Design an avatar upload pipeline using synthetic images. Rename files server-side, cap size, decode and validate the intended image format with a maintained library, and keep storage outside executable routes. Test a misleading extension, excessive size, and another user's image URL. Each test should target a separate boundary.
A successful malware scan is not a universal proof that uploaded content is safe to parse, execute, or display.
Why store uploaded content outside executable application paths?
So accepted bytes cannot automatically become server-executed code
So all files become confidential without access checks
So file-size limits are unnecessary
Storage and execution must remain separate. Access control, validation, and resource limits are still needed.

W09
XML stores structured data using elements and attributes. Some parsers also support external entities: references to resources outside the document. With unsafe configuration, untrusted XML can use those references to reach unintended resources; this is XML external entity injection (XXE). Other XML features may consume excessive resources even when no file is disclosed.
Use the platform's documented safe parser configuration for untrusted XML. Disable unnecessary external resolution and document-type features, apply resource limits, and validate the application structure. A format being well-formed says nothing about whether its parser should access files or networks. JSON may simplify some interfaces, but changing formats does not eliminate ordinary validation needs.
For a harmless local parser exercise, accept a fixed small record structure. Test a normal record, unexpected fields, oversized nesting, and a document containing a declaration that your safe configuration should reject. Confirm the parser makes no unexpected resource access using the provider's controlled lab, rather than relying only on the displayed error.
XML schema validation and external-entity configuration solve different problems. Do not assume enabling one disables the other.
Which capability should an untrusted XML parser usually avoid unless explicitly required?
Resolving external entities through filesystem or network access
Reading ordinary permitted element text
Reporting malformed syntax
External resolution introduces additional resource and trust boundaries beyond the submitted document.

W10
A server may be allowed to fetch resources that the user cannot reach directly. Server-side request forgery (SSRF) abuses that access by influencing where the server sends a request. A URL chooses a scheme, destination and port, and may involve credentials or redirects. Check those meanings under the actual parser and fetch behaviour, rather than treating the URL as ordinary display text.
Prefer fetching from fixed known services or mapping IDs to approved resources. Where arbitrary destinations are required, validate supported schemes and destinations, account for name resolution and redirects, and enforce network-level egress restrictions. Revalidate each relevant hop. Cloud metadata and internal services need their own protections; a URL filter should not be the only boundary.
Design a local thumbnail service that accepts IDs for a fixed image catalogue instead of free-form URLs. For the linked lab, record the server's network position and which boundary the unintended request crosses. Compare initial destination validation with redirect handling and explain why checking only the visible input string is incomplete.
An apparently public hostname can resolve differently over time. Destination policy must consider the address actually used and subsequent hops.
Why is SSRF dangerous even when the response is not returned to the caller?
The server may still perform an unintended action or reach a protected service
A hidden response guarantees no effect occurred
Only browser-origin rules determine server-side access
The request itself may have side effects or cross a network trust boundary, regardless of response visibility.

W11
An API documents operations and the data they accept. For an operation involving an object ID, the server must check whether the current user may act on that object. A hard-to-guess ID can make discovery harder, but it is not a permission check. Someone can still copy, leak or reuse an ID from another account.
Validate type, range, allowed fields, relationships, and requested operation. Avoid mass assignment, where arbitrary supplied fields automatically become object attributes. Separate response schemas from internal storage schemas so sensitive fields are not returned accidentally. Test the same operation with multiple controlled identities and object ownership combinations.
Create two synthetic accounts and one private note per account. Build a test matrix for read, update, and delete using each identity and each note ID. Add an unexpected owner_id field to a local update request and ensure the server does not silently reassign ownership. Record the expected result for every row before running the tests.
API documentation describes intended behaviour; it does not enforce it. The implementation must reject forbidden combinations.
What should happen when a valid user supplies another user's private object ID?
The server applies object-level permission checks and denies unauthorised access
The ID's existence automatically grants access
The browser decides whether the database should return it
The server must evaluate the actor-object-action relationship on every relevant operation.

W12
An account needs protection throughout its life: registration, login, sessions, recovery, factor changes and closure. A strong login does little good if a weak recovery route grants the same access. Account enumeration means revealing whether an account exists through replies, timing or side effects. Assess the harm in the context of the system’s threat model.
Use established framework mechanisms for credential handling, secure session rotation, recovery tokens, and appropriate rate limits. Recovery tokens need sufficient unpredictability, a limited lifetime, and carefully enforced single use. Protect factor changes as sensitive actions. Error messages should avoid unnecessary disclosure while remaining usable for legitimate users.
Draw a test account's normal login and lost-password paths. For a local recovery flow, test an expired token, a reused token, and a token presented for the wrong account. Confirm that a successful reset changes the intended credential and follows the application's session-revocation policy. Use only synthetic accounts in the training environment.
A recovery message can be generic while other observable differences still reveal account existence. Examine the complete behaviour.
Which path deserves the same security attention as normal login?
Password and multifactor recovery
Only the public colour-theme switch
Only the site's logo download
Recovery can confer account access, so its authority and abuse resistance are part of authentication security.

W13
Access control checks which actions a user may take, not merely which pages they may open. Horizontal escalation reaches another peer’s resources; vertical escalation reaches a more privileged role. A user can be signed in and send a correctly formatted request that still breaks a business rule. Check the action and ownership, not just the login.
Write invariants in plain language before testing. For example, an invitation can grant only the permissions the inviter is allowed to delegate, and a refund cannot exceed the amount paid. Enforce checks in the operation that changes state. Do not trust role names, prices, ownership fields, or workflow state supplied by the client.
Model an invitation flow with owner, editor, and viewer roles. Define who may invite whom and which roles may be granted. Test each permitted and forbidden transition with controlled accounts. Include a viewer directly calling the invitation endpoint, rather than assuming a hidden button prevents that action.
Checking permissions only on page rendering leaves direct API requests unprotected.
Where should the rule 'a viewer cannot grant editor access' be enforced?
In the server operation that creates or changes the invitation
Only by hiding the editor option in HTML
Only in a welcome email
The state-changing operation must enforce the rule regardless of how the request was constructed.

W14
A JSON Web Token (JWT) carries structured claims. A typical signed compact JWT has an encoded header, payload and signature. Encoding lets you read those claims; it does not keep them secret. To trust a signature, the verifier must use the intended algorithm and a trusted key, then validate the relevant claims. A readable token is not a validated token.
Validate the token's issuer, audience, time constraints, algorithm policy, and purpose according to the protocol. Key selection must not become an arbitrary caller-controlled file or network lookup. A correctly signed token for a different service should not automatically work here. Consider revocation, rotation, and how long a stolen bearer token remains usable.
Decode a synthetic course token without treating decoding as verification. List which claims are visible. Then use the provider's supported verification library to test valid, expired, wrong-audience, and altered tokens. Document the trusted key source separately from any untrusted key identifier in the token header.
A library returning decoded JSON may not have verified authenticity. Read the API contract carefully.
Does base64url-decoding a JWT establish its authenticity?
No; signature and claim validation are separate required checks
Yes; readable JSON is proof of a valid signature
Yes; a token with three parts cannot be altered
Decoding only interprets the representation. Verification establishes integrity under a trusted key and validation policy.

W15
OAuth lets an application receive limited access to a resource on someone’s behalf. It is not, by itself, a complete login identity protocol. OpenID Connect adds an identity layer with its own tokens and checks. Draw the resource owner, client, authorisation server and resource server, then follow which party receives each code or token.
An authorisation-code flow uses carefully registered redirect URIs and transaction binding. PKCE binds code redemption to the client instance holding a verifier, helping resist code interception. State and applicable protocol-specific checks bind a response to the initiating interaction. Use maintained libraries and current provider guidance instead of inventing a flow from isolated redirect examples.
Draw a modern authorisation-code flow with PKCE using a synthetic account in the course lab. Label the authorisation code, verifier, access token, and any ID token. Explain why an access token for one API is not automatically a valid login assertion for a different client. Test the lab's mismatched redirect or transaction case within scope.
Access tokens and ID tokens have different audiences and purposes. Similar-looking token formats do not make them interchangeable.
What does PKCE help bind?
Authorisation-code redemption to possession of the initiating client's verifier
All API permissions to the user's display name
A password to every unrelated website
The code challenge and verifier connect code redemption to the initiating client instance under the flow's assumptions.

W16
Suppose a coupon may be redeemed once. Two requests can both read “unused” before either saves “used”, so both appear allowed. This is a web race condition: overlapping operations break a rule about the system’s state, called an invariant. Validating the request format cannot solve a mistake in how those operations interleave.
Use atomic database operations, transactions with appropriate isolation, uniqueness constraints, or carefully designed locking to preserve the relevant invariant. Idempotency makes repeated equivalent requests have one intended effect, but requires a trustworthy key scope and stored result. Merely slowing requests down or adding a client-side button lock does not establish correctness.
Model one-use redemption as unused → used. Draw two requests both observing unused, then both granting credit. Repair the local model with an atomic conditional update or an appropriate unique constraint and transaction. Test overlapping requests in the authorised lab and verify the final ledger, not just the number of successful HTTP responses.
A transaction boundary alone does not imply the isolation level needed for every invariant. State the guarantee you rely on.
What must a single-use redemption protect?
The eligibility check and state change as one invariant-preserving operation
Only the visual button's disabled state
Only the time between two browser clicks
The server must prevent competing operations from both consuming the same entitlement.

W17
A proxy and a backend must agree on where each HTTP request ends. Request smuggling exploits a disagreement about that message framing. The components can then interpret the same bytes as different requests, potentially affecting another request. Study the whole proxy chain before treating one unusual response as proof of the cause.
Use current maintained servers and consistent protocol handling, reject ambiguous framing, and follow the deployment platform's guidance. Connection reuse and protocol translation can change exposure. This is an advanced topic because HTTP semantics, transport streams, intermediary behaviour, and isolation all interact. Keep experiments inside provider-supplied labs where no unrelated users share the connection path.
Draw a frontend-to-backend byte stream containing two harmless requests. Mark the boundary each component expects under the lab's controlled disagreement. Explain how the two interpretations diverge without testing public infrastructure. For the remediation exercise, state which component rejects ambiguity and verify the normal request path still functions.
A timeout alone is not proof of request smuggling. It may reflect many unrelated parser or network behaviours.
What is the central failure behind request smuggling?
Intermediaries disagree about request framing boundaries
The browser uses a long password
A database table lacks an index
Different framing interpretations let bytes acquire unintended meaning across shared connections.

W18
An application assessment brings individual weaknesses back to the system’s security rules. Start with the agreed scope, valuable assets, roles, data flows and business rules. List the operations before choosing tests. A useful finding explains which property failed, under what conditions, how the evidence can be reproduced and what the failure allows.
Separate discovery from reporting. Keep baseline requests, controlled account identities, timestamps, and minimal evidence. Confirm findings independently and avoid counting several symptoms of one root cause as unrelated successes. A repair is incomplete until it preserves legitimate behaviour and rejects the original unauthorised operation and meaningful variants.
Assess the supplied application using an owner, a second user, and a logged-out session. Cover input handling, ownership, authentication lifecycle, cross-origin behaviour, file boundaries, and concurrent state changes. Rank findings by supported impact and likelihood. Repair at least one issue, add a regression check, and ask the other learner to reproduce the finding from the report alone.
A long tool output is not an assessment report. Explain which observed behaviour violates which rule and what evidence supports that conclusion.
What best demonstrates a finding is reproducible?
Another learner can follow the scoped report and observe the same violated property
The original tester remembers the steps
The scanner lists many severity labels
Independent reproduction checks that the report contains sufficient evidence and instructions rather than relying on hidden knowledge.
