S01
Threat modelling means asking how a particular system could fail and what should protect it. Start with the service and its users, rather than a shopping list of security tools.
Identify assets, information flows, permissions and unwanted events. Connect each protection with a specific threat and revisit the model when the system changes.
Draw a private notes service with browser, server, database, and backup store. Mark where identity is established and where note ownership is checked. Consider a stolen session and an accidental public backup. Add one preventive and one recovery control for each, and explain the residual risk after those controls fail or succeed.
A threat model is a revisable argument, not a guarantee. Update it when data flows, dependencies, or assumptions change.
Which is the strongest starting point for a threat model?
The system's assets, behaviour, actors, and trust boundaries
A list of fashionable security tools
A promise that the framework is secure by default
Controls make sense in relation to what the system must protect and where untrusted influence enters.

S02
Encryption protects a message from readers who lack the key. Authenticated encryption also detects unauthorised changes under the scheme's rules.
Protect keys, satisfy the scheme's nonce rules and verify authenticity before using decrypted data. Use cryptographic randomness where required.
With the course's supported cryptography library, encrypt a harmless message and authenticate a record identifier as associated data. Decrypt successfully, then alter the ciphertext or identifier and confirm authentication fails. Record the nonce-generation rule and key lifetime. Treat any authentication failure as failure, not as permission to display partially decrypted content.
Encryption is not a substitute for key management. An exposed key can erase the intended protection.
What should happen when AEAD authentication fails?
Reject the message without using unauthenticated plaintext
Return the plaintext with a warning and continue
Ignore the failure if the ciphertext looks readable
AEAD's authenticity guarantee depends on rejecting failed verification before relying on the data.

S03
Hashes, message authentication codes and password-storage methods solve different problems. Choosing the right one starts with what you need to verify.
Use an unkeyed hash for a stated fingerprinting goal, a keyed MAC for shared-key message authentication, and an appropriate costly function for password storage.
Hash two different harmless messages and compare digests. Then authenticate a message using a standard MAC API and verify that a changed message fails. Finally use the course's password-storage API to store and verify a synthetic password twice with different salts. Explain why unequal stored values can still verify the same password.
A plain hash does not prove who created a message. Anyone able to change the message may also recompute its unkeyed digest.
Why use a unique salt for password hashing?
To prevent reuse of one precomputed guess result across many stored passwords
To make a weak password impossible to guess
To encrypt the password so it can always be recovered
Salts separate stored computations. They do not add password entropy or turn hashing into reversible encryption.

S04
Public-key cryptography separates a public key that may be shared from a private key that must remain protected. Different operations use those keys for different purposes.
Distinguish signatures, key agreement and encryption. Verify the binding between a public key and the intended identity, not just the signature calculation.
Paper signature fixture: the trusted contact directory assigns key K to Alice. A verifier reports that K verifies the statement approve note1 and rejects the changed statement approve note2 under the same signature. State what that supports about the signed bytes. Then remove the trusted directory entry: explain why verification alone no longer establishes the name Alice. K is a label, not a usable cryptographic key.
A signature establishes a relationship to a key under assumptions. Its human identity meaning depends on trustworthy key distribution.
What does successful signature verification directly establish?
The message matches a signature produced with the corresponding private key, under the scheme's assumptions
The message is confidential
The signer is necessarily a trustworthy person
Verification binds data to a key. Confidentiality and the real-world identity or trustworthiness of the signer require separate reasoning.

S05
TLS helps a client and server establish a protected communication channel. HTTPS uses that channel for HTTP, but the application still needs its own input and permission checks.
Verify the intended endpoint, establish a protected channel and identify where it terminates. Continue enforcing application security inside that channel.
Draw browser → proxy → application server. Assume TLS protects browser-to-proxy and plain HTTP connects proxy-to-server. Mark plaintext inside both endpoints and on the second connection. Then replace the second segment with TLS and identify which transit exposure changes. This diagram needs no real website or certificate-warning bypass.
HTTPS does not establish that an application's business logic, dependencies, or content are safe.
A proxy terminates TLS and forwards plain HTTP internally. Where is the original TLS protection boundary?
Between the client and that proxy
Automatically through every downstream service and database
Only around the visible HTML, excluding requests
TLS protects its actual connection endpoints. A downstream connection is a separate channel with separate guarantees.

S06
Signing in answers who the user is. Authorisation answers what that user may do. A person can be correctly signed in and still have no right to open another person's record.
Use a trusted identity, then check that identity's permission for this action on this object. Enforce the rule at the server or database access point.
For this separate fictional policy, owners may read/edit/delete their own notes; invited readers may only read the notes they are invited to; administrators may disable accounts but may not read note bodies. Evaluate A owning note1, B invited to read note1, C admin, and D with an expired session. Write one allow and one deny case for each relevant role, and explain why D needs sign-in before any ordinary note action.
Being signed in is not a universal access permission. A valid identity must still be evaluated against each protected operation.
A signed-in learner can edit another learner's private notes. Which control is missing?
Object-level authorisation
Text formatting
A larger password field
The identity may be valid, but the requested action on that particular object lacks permission.

W01
Developer tools and an intercepting proxy help you see the requests an application sends. A useful inspection connects each request with a user action and the server's actual response.
Map actions to requests, identify the observation point and change one lab value to answer a specific question. Check the result against the intended rule.
In a provided training lab, capture a harmless form submission. Repeat it unchanged, then alter one non-sensitive input and compare the response and server-side result. Label each request so the original remains available. Explain which observations are direct evidence and which explanations are hypotheses requiring another check.
An unusual response is not automatically a vulnerability. Establish the violated security property and reproduce it within scope.
Why preserve an unmodified baseline request?
It provides a comparison for attributing the effects of later changes
It guarantees every later response is exploitable
It removes the need to identify the active account
A baseline helps separate normal behaviour from effects caused by a controlled change.

W02
SQL injection happens when supplied data is interpreted as part of a database instruction. Passing input values separately from SQL syntax prevents that class of confusion at the query boundary.
Keep SQL structure trusted and bind external values through the database API. Use allowlisted mappings for identifiers and restrict the application's database permissions.
Use the linked deliberately vulnerable lab, then repair a local query by replacing string concatenation with the database driver's binding API. Test a normal name, a quote-containing name, and the lab's authorised failure case. The corrected version should preserve legitimate punctuation while preventing input from altering query structure.
Deleting quote characters is not a general SQL injection defence and may damage valid data.
What is the primary purpose of SQL value parameters?
Keep input values separate from query syntax
Encrypt the database connection automatically
Grant every query administrator permissions
Binding preserves the code-data boundary. Connection encryption and account permissions are separate controls.

W03
Cross-site scripting happens when an application lets supplied content run as script in another user's browser. The key question is where data stops being treated as text.
Trace supplied data to its browser interpretation point. Use safe text handling or a suitable sanitiser for the intended context, with additional policy restrictions as support.
In a local preview component, compare assigning a harmless tag-like string through textContent with inserting it as HTML. Draw the source-to-sink path without using real users or public targets. Replace the unsafe sink, then test ordinary text, angle brackets, quotes, and non-ASCII input to ensure the repair preserves intended content.
One generic escaping function is not appropriate for every output context.
A comment is meant to display plain text. Which browser API best preserves that intention?
textContent
An unrestricted innerHTML assignment
Executing the comment with eval
textContent creates text rather than asking the browser to interpret the value as markup or code.

W04
A browser may attach sign-in cookies automatically. Cross-site request forgery tries to use that behaviour to make a signed-in user's browser send an unwanted action.
Automatically attached credentials are not proof of intended action. Verify the request's expected context and use appropriate CSRF protections for cookie-authenticated writes.
For the provided lab, list the credentials sent automatically, the action changed, and the missing intent check. In a local repair, enable the framework's CSRF middleware and test a legitimate form, a missing token, and an incorrect token. Confirm the failed requests do not change server state.
Same-origin restrictions on reading responses do not necessarily stop a browser from sending cross-origin requests.
Why can CSRF work even when the attacker cannot read the response?
The harmful effect may occur when the authenticated request is processed
Every request requires the attacker to see the response first
The same-origin policy blocks all cross-origin form submissions
The attacker may need only the side effect. Read restrictions and request-sending rules are different.

W05
Browser origin rules restrict which pages can read each other's data. CORS lets a server explicitly relax some cross-origin reading rules; it is not a replacement for sign-in or access checks.
Use origins to explain browser access boundaries. Configure CORS deliberately and keep server-side identity and ownership checks independent.
Draw a frontend on one origin and an API on another. Define exactly which origin needs readable responses. Test the allowed origin and a disallowed origin using the course lab. Record network activity separately from script-visible results so that a blocked read is not mistaken for proof that no request reached the server.
CORS does not replace API access checks and is not enforced by arbitrary server-side HTTP clients.
Who primarily enforces CORS restrictions on response access?
The browser
Every command-line HTTP client by universal rule
The database engine
CORS is a browser security mechanism. The server still needs authentication and authorisation for direct callers.

W06
A path supplied by a user should not let a program escape the files it is meant to access. Path traversal occurs when path interpretation crosses that boundary.
Map requests to allowed files, check ownership and verify the actual resolved access stays within the intended filesystem boundary.
Inside the provided lab, identify the intended base directory and the point where input becomes a filesystem lookup. For a local repair, replace user-supplied paths with opaque IDs mapped to known files. Test a legitimate ID, an unknown ID, and boundary cases. Verify both the response and which file was actually accessed.
Removing one occurrence of '../' is not a reliable containment strategy. Normalisation and alternate representations can defeat ad hoc filtering.
Which design most directly reduces arbitrary path interpretation?
Mapping an opaque identifier to an application-controlled stored object
Appending input to a base path without checking
Removing only the first parent-directory component
An identifier mapping narrows the operation to known resources instead of treating caller input as path syntax.

W07
Command injection happens when supplied text becomes an instruction to a command interpreter. Keep user data separate from program selection and command syntax.
Prefer a direct library call. When a subprocess is required, fix the executable, separate arguments from syntax and validate the called program's own options and resource use.
Replace a local shell-based file-counting operation with a language library call. Compare handling of spaces and punctuation in harmless filenames. If the lab requires a process, pass explicit arguments and inspect the tool's end-of-options rules. Explain which interpreter was removed and which input semantics still remain.
Avoiding a shell is a strong improvement, not proof that all possible argument injection has disappeared.
What is the best first alternative to constructing a shell command for a file operation?
Use a language library API for the operation
Add more string concatenation
Run the command with greater privileges
A direct API avoids an unnecessary command language boundary and usually makes validation clearer.

W08
An uploaded file is untrusted data. A safe upload feature checks who may upload it, what it contains, where it is stored and how it will later be served.
Validate the intended file purpose, isolate storage and processing, and enforce access when serving the result. Treat every stage of the upload lifecycle as part of the feature.
Design an avatar upload pipeline using synthetic images. Rename files server-side, cap size, decode and validate the intended image format with a maintained library, and keep storage outside executable routes. Test a misleading extension, excessive size, and another user's image URL. Each test should target a separate boundary.
A successful malware scan is not a universal proof that uploaded content is safe to parse, execute, or display.
Why store uploaded content outside executable application paths?
So accepted bytes cannot automatically become server-executed code
So all files become confidential without access checks
So file-size limits are unnecessary
Storage and execution must remain separate. Access control, validation, and resource limits are still needed.

W09
A data parser does more than recognise punctuation. Some formats can request external data or expand complex structures, so configure the parser for the feature you actually need.
Accept only the document capabilities the feature needs. Control external resolution, expansion and resource use, then validate the parsed values.
For a harmless local parser exercise, accept a fixed small record structure. Test a normal record, unexpected fields, oversized nesting, and a document containing a declaration that your safe configuration should reject. Confirm the parser makes no unexpected resource access using the provider's controlled lab, rather than relying only on the displayed error.
XML schema validation and external-entity configuration solve different problems. Do not assume enabling one disables the other.
Which capability should an untrusted XML parser usually avoid unless explicitly required?
Resolving external entities through filesystem or network access
Reading ordinary permitted element text
Reporting malformed syntax
External resolution introduces additional resource and trust boundaries beyond the submitted document.

W10
A server may fetch a web address for a user. Server-side request forgery occurs when that user can make the server reach destinations it should not access.
Control the actual destinations the server can reach, including redirects and resolution. Limit the fetcher's network authority and resource use.
Design a local thumbnail service that accepts IDs for a fixed image catalogue instead of free-form URLs. For the linked lab, record the server's network position and which boundary the unintended request crosses. Compare initial destination validation with redirect handling and explain why checking only the visible input string is incomplete.
An apparently public hostname can resolve differently over time. Destination policy must consider the address actually used and subsequent hops.
Why is SSRF dangerous even when the response is not returned to the caller?
The server may still perform an unintended action or reach a protected service
A hidden response guarantees no effect occurred
Only browser-origin rules determine server-side access
The request itself may have side effects or cross a network trust boundary, regardless of response visibility.

W11
An API should accept only the operations and fields a user is allowed to control. A valid request shape does not prove access to the object it names.
Validate the operation, check access to each selected object and allow only intended writable fields. Apply limits to queries as well as individual records.
Create two synthetic accounts and one private note per account. Build a test matrix for read, update, and delete using each identity and each note ID. Add an unexpected owner_id field to a local update request and ensure the server does not silently reassign ownership. Record the expected result for every row before running the tests.
API documentation describes intended behaviour; it does not enforce it. The implementation must reject forbidden combinations.
What should happen when a valid user supplies another user's private object ID?
The server applies object-level permission checks and denies unauthorised access
The ID's existence automatically grants access
The browser decides whether the database should return it
The server must evaluate the actor-object-action relationship on every relevant operation.

W12
Signing in, resetting a password and recovering an account are all ways into that account. Protect the whole journey rather than only the main password form.
Review sign-in and recovery as one system. Protect tokens, limit abuse, control account disclosures and verify what happens to existing sessions.
Draw a test account's normal login and lost-password paths. For a local recovery flow, test an expired token, a reused token, and a token presented for the wrong account. Confirm that a successful reset changes the intended credential and follows the application's session-revocation policy. Use only synthetic accounts in the training environment.
A recovery message can be generic while other observable differences still reveal account existence. Examine the complete behaviour.

Password and multifactor recovery
Only the public colour-theme switch
Only the site's logo download
Recovery can confer account access, so its authority and abuse resistance are part of authentication security.

W13

W14
A JWT is a token format that carries claims. Those claims become useful evidence only after the application verifies the token and checks that it is appropriate for this operation.
Decode only to inspect. Verify the allowed algorithm and key, check issuer, audience, time and purpose, then perform the normal permission decision.
Decode a synthetic course token without treating decoding as verification. List which claims are visible. Then use the provider's supported verification library to test valid, expired, wrong-audience, and altered tokens. Document the trusted key source separately from any untrusted key identifier in the token header.

Does base64url-decoding a JWT establish its authenticity?
No; signature and claim validation are separate required checks
Yes; readable JSON is proof of a valid signature
Yes; a token with three parts cannot be altered
Decoding only interprets the representation. Verification establishes integrity under a trusted key and validation policy.

W17
