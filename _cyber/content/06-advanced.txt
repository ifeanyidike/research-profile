A01
A distributed system can lose a reply even after completing an action. Safe retries need a way to distinguish repeating a request from performing the action again.
Treat missing replies as uncertain outcomes. Bind retries to a stored operation identity and reconcile state before repeating an important effect.
Model a payment-like transfer using only synthetic balances. The server commits the debit, but the response is lost. The client retries. Show how a naive implementation debits twice. Add a scoped idempotency key and stored result, then consider a crash before and after each write. State which updates must share an atomic boundary.
A timeout is uncertainty, not proof of failure. Treating it as a clean rollback can create duplicate actions.
After a request times out, what can the client safely conclude about server completion?
It is uncertain without additional protocol evidence
The operation definitely never ran
The operation definitely ran exactly once
The response may have been lost after completion, or the operation may not have completed. The protocol must resolve the uncertainty.

A02
A cryptographic proof supports a precisely defined claim under stated assumptions. It does not prove that every implementation or use of the construction is secure.
State the security game, attacker powers, assumptions and bound. Follow the reduction's reasoning, then separately check whether a real implementation meets its model.
For a course encryption game, write challenger and adversary steps in plain language. Identify the hidden bit, allowed queries, winning condition, and baseline guessing probability. Change one assumption, such as allowing a forbidden decryption query, and explain why the definition would collapse or need revision. Keep toy arithmetic separate from production implementation.
A proof for a primitive under one attack model does not automatically prove an entire deployed system secure.
What must a meaningful cryptographic security claim specify?
The adversary model, winning condition, assumptions, and resource bounds
Only the ciphertext's apparent randomness
Only the key's filename
Security is defined relative to a game and assumptions. Appearance and naming do not establish the claim.

A03
Automated analysis can find defects by generating inputs, inspecting code or following possible paths. Each method sees some problems well and misses others.
Choose an analysis method for a defined property, validate reported cases and explain what code, inputs and environment the method actually covered.
Use a tiny local parser with a known boundary defect. Run the course's non-model fuzzing exercise in the isolated lab, minimise a failing input, and add a regression test. Compare the discovered path with a static warning or symbolic condition. Explain which program behaviours each method did not examine.
High code coverage is an exploration metric, not proof that all important states or semantic properties were checked.
Why minimise a fuzzing failure?
To isolate a small reproducible input that clarifies the defect
To guarantee the defect affects every production system
To avoid understanding the parser's requirements
A smaller reproducer helps establish causality, repair the bug, and maintain a focused regression test.

A04
Security also depends on hardware, physical access and information leaked indirectly. A correct abstract algorithm may reveal secrets through how it runs.
Name the trusted starting components and attacker observations. Check indirect leakage and physical assumptions alongside abstract algorithm correctness.
Use a harmless simulation of a two-level memory hierarchy. Record the differing costs of a hit and a miss, then show how a secret-dependent array choice can influence observed time. Explain what a real experiment would need to control and why the toy result alone does not demonstrate an attack on actual hardware.
The absence of a direct memory read does not rule out information leakage through observable side effects.
Why can secret-dependent memory access leak information?
It may change shared cache state and observable timing
Caches always publish plaintext keys in log files
Virtual memory guarantees identical execution time
A secret can influence an observable resource pattern without being directly readable by the observer.

A05
Formal methods express a system's rules precisely enough to reason about them systematically. The first job is to choose the property the model should preserve.
State a meaningful property, define the state and transitions, then interpret proof or counterexample within the model's actual scope.
Specify a two-client single-use token model. Include read, consume, and retry transitions, then ask the checker whether consumption can occur twice. Inspect the counterexample trace from the naive model. Repair the transition to preserve the invariant and rerun the bounded model. Record constants and assumptions so another learner can reproduce the result.
A successful bounded check establishes a result for the checked model and configuration, not all possible deployed environments.
What is the most useful result of an invariant counterexample?
A trace of modeled transitions that reaches a violating state
A guarantee that the programming language is unusable
A proof that every implementation has the same defect
The trace explains how the modeled behaviour breaks the property and guides revision of the model or design.

A06
Mobile security depends on app permissions, local storage, network use and the platform's trust rules. A secure design follows data across those boundaries.
Track platform permissions, app entry points, credential storage and server authority together. Interpret the sandbox and release guarantees for the actual mobile platform.
Threat-model a hypothetical mobile notes app. Draw local storage, OS key storage, authentication provider, API, backups, and update channel. Explain what remains protected if the phone is locked, if the user unlocks it for an attacker, or if the account is compromised. Avoid claiming one storage API solves all three scenarios.
Obfuscation may raise reverse-engineering effort but does not make a secret embedded in a distributed app reliably private.
Where should a mobile API enforce object ownership?
On the backend, independent of the app's interface
Only in the app's hidden buttons
Only in the app-store description
Clients can be modified or replaced. Server-side permissions must protect the data regardless of the client.

A07
When computers control physical processes, a security failure can affect safety and availability as well as information. Testing and response must respect those consequences.
Trace data to physical effects, define safety and timing requirements with domain expertise, and keep learning tests inside their expressly authorised simulated scope.
Model a simulated water-level controller with sensor, controller, actuator, and operator. Define a safe range and describe the effect of stale measurements, delayed commands, and lost connectivity. Propose a monitoring and recovery plan in the simulation. Explain why scanning or rebooting real operational equipment without an agreed procedure is outside the exercise.
Protecting confidentiality alone may leave severe physical safety and service-continuity risks unaddressed.
Why can ordinary IT incident actions require extra care in operational technology?
They may disrupt physical processes with timing and safety constraints
Operational equipment never uses networks
Physical systems have no integrity requirements
Containment and recovery must account for the process's hazards and operational requirements.

R01
A security paper makes a claim under a threat model and supplies evidence. Read by connecting those three parts instead of treating the headline as a general promise.
Connect each claim with its threat model and evidence. Record assumptions, comparison conditions and limits before deciding how the work applies elsewhere.
Create a one-page claim-evidence table for the assigned paper. For each major claim, identify the supporting figure, theorem, or experiment and one limitation. Trace one reported result back to its setup and denominator. Explain the method to your partner without reading the abstract aloud, then answer their strongest counterexample.
Peer review and a respected venue do not eliminate the need to examine assumptions, measurements, and reproducibility.
Which question best tests a paper's empirical claim?
Does the reported experiment and metric actually support the stated conclusion?
Does the title contain a fashionable term?
Can the abstract be repeated from memory?
A research critique connects a precise claim to the method and evidence that justify it, including limitations.

R02
A reproducible research artifact lets another authorised person understand how a result was obtained. It connects the question, source version, inputs, method and limitations.
Package method and evidence together, preserve failures and scope limits, and make permission and safe reuse part of the research design.
Using only an offline synthetic dataset, package a small detector comparison. Give your partner a fresh setup procedure and ask them to reproduce the table from raw data. Record every undocumented step they needed. Revise the artifact, explain differences between runs, and state what the synthetic population cannot establish about production performance.
Reproducible numbers can still answer the wrong question or reflect a biased dataset. Method and relevance need separate scrutiny.
What should another learner receive to reproduce an analysis?
Raw or lawfully accessible data, code, environment details, configuration, and exact steps
Only the final chart
Only a statement that the experiment worked
The artifact must expose the path from inputs to results, including the environment and assumptions.

R03
A strong security capstone shows that you can understand a system, defend a clear claim and explain the evidence and limits. Choose depth around one coherent problem.
Choose one coherent security claim, implement and test its controls, preserve the evidence and defend both the result and its remaining assumptions.
Ask your partner to act as an independent reviewer. They should set up the project from your instructions, attempt the documented assessment, explain one trust boundary, and challenge one design assumption. Respond with evidence or an explicit limitation. Finish with a defended report and a next-study plan naming the prerequisites for your chosen specialisation.
A completed checklist is not the same as an independently defensible system. The explanation and reproducible evidence are part of the work.
What is the strongest capstone outcome?
A scoped system and report another learner can reproduce, test, and critically challenge
A screenshot showing every video marked watched
A claim of expertise across all cybersecurity fields
Independent reproduction and defence test understanding, implementation, and the limits of the conclusions.
